## Phase 4: Anomaly Detection

- [x] **T19: CPU anomaly detector (vertical: event stored + listed)** (M)
  - Done. Pure logic in `core/anomaly/{mod,rules,cpu,tracker}.rs`; `storage/migrations/0008_anomaly_events.sql`, `repo/anomalies.rs` (events + `usable_cpu_baselines`), `storage/detect.rs` (`DetectingSink` wraps `DbSink`); CLI `winperf anomalies list [--hours N] [--limit N]` and `anomalies show <id>`; `monitor run` has detection on.
  - Rule: a subject's CPU (instances summed per executable) is elevated above max(absolute floor, median + z x 1.4826 x MAD (spread at least 0.5 points), p95 x factor). Normal: floor 5%, z 6, p95 x 1.5, sustained 120 s. Low: 10%, z 10, x 2.0, 300 s. High: 3%, z 4, x 1.2, 60 s. One quiet tick is tolerated; two restart the clock. One event per episode; it re-arms after the process calms down. CPU sensitivity follows `[detection]` (`cpu` override, else the global value).
  - Gating: baselines are read every 5 min; a subject takes its longest configured window whose confidence is above Insufficient, otherwise it is never judged. Profiling mode (`profile start`) pauses detection and drops episodes in progress; sampling continues.
  - Event has every FR-018 field: pid, name, path, resource, measured, baseline median, deviation %, duration, system CPU and memory in use, timestamp, severity, explanation, plus the baseline window and confidence it was judged against. Application name is filled when the instance is linked to an installed application (not yet populated by anything).
  - Verified: scenario tests (brief spike: none; 0.5% to 2%: none; 8% to 72% for 3 min: one event at the 2 min mark; one dip tolerated, two restart; absent subject counts as quiet; no baseline / Insufficient / profiling: none; instances summed, busiest named); end-to-end through the engine and database; live: 4 busy pwsh.exe processes (23.3% of the machine) against a copy of the 4 h soak DB raised exactly one Warning event after 2m 00s, tick cost 27 ms. Full `check.ps1` passes.

Deviation for a near-zero baseline is huge (+23250%) because the baseline is floored at 0.1%; the explanation says "233.5x" which reads better, consider showing that instead. Baseline contamination: the longest window includes the recent past, so a slow multi-day drift raises the baseline; median/MAD limit the effect. The event's instance link is NULL if the instance row had not been flushed yet (up to 30 s buffering).
  - Original spec:
  - AC: fires only when (value > baseline-by-robust-z or ratio) AND > absolute floor AND sustained ≥ duration; sensitivity Low/Normal/High presets; suppressed when confidence is Insufficient; event has all FR-018 fields and a human-readable explanation; `winperf anomalies list`.
  - Verify: scenario tests: brief spike → no event; 0.5%→2% → no event; 8%→72% for 3 min → event; CPU burner end-to-end.
  - Deps: T17, T18. Files: `core/anomaly/{mod,cpu,rules}.rs`, `storage/repo/anomalies.rs`, migration 0003.

## Phase 7: Hardening

- [x] **T34: Retention, aggregation (1-min, 15-min), pruning, VACUUM policy** (M)
  - Done (schema v11, `0011_rollups.sql`; `repo/maintenance.rs`). Tables `process_rollups` (per instance, per bucket: tick count, avg and max of CPU, working set, private bytes, process I/O read and write, network rx and tx) and `system_rollups` (avg/max of the system metrics), at 60 s and 900 s widths, plus `maintenance_state` watermarks; no foreign key to instances (a delete must not scan them). `Database::maintain(now, retention, limits)` = `rollup_minutes` (complete minutes only, one minute of grace, a chunk of an hour per transaction, rebuilding a bucket replaces it) then `rollup_quarters` (tick-weighted means over the minutes that measured the value, max of maxes) then `prune`: raw samples only when older than `raw_samples_days` AND already rolled up, 1-minute rows only when older than `aggregate_1min_days` AND already in 15-minute rows, 15-minute rows by age, resolved anomalies older than `anomaly_days`, ended process records older than the 15-minute retention (foreign keys switched off on that connection for the delete, as the Checkpoint 2 note required), in 20,000-row batches, then a passive WAL checkpoint. Nothing is deleted that is not safely covered, so a stopped job never costs history.
  - Running it: the recorder (`winperf-runtime`) starts a maintenance thread with its own connection: first pass a minute in, then every minute, every 5 s while a pass left work (so the backlog after upgrading is worked off in pieces of 6 hours of raw data). `winperf maintain [--vacuum]` runs it to completion by hand; `--vacuum` (rewrite the file to give space back to the disk) refuses while a recorder holds the database. Normal operation does not vacuum: freed pages are reused, so the file settles at a steady size.
  - Reading: `Database::history_source(from)` picks raw samples, or the finest rollup, only when a rollup reaches back past the raw samples (a short history is never shown coarser than it is). Used by `/api/system` (also the anomaly page's system charts and the history export), the rankings and the application page; the answers carry `resolution_ms` and the page says when it shows N-minute averages (peaks are then the highest bucket average, or for rankings the sum of per-process bucket maxima). Baselines: a window longer than the raw retention (the 168 h window with 2 days of raw) is computed from the 1-minute rollups (`recompute_baselines_from`, used by the schedule and `baseline update`), the shorter ones from raw ticks exactly as before. Databases without the rollup tables are read as raw.
